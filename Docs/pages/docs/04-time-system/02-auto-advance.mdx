# Auto-advance

By default, `MockTimeSystem` advances its clock every time the code under test waits. A call to `Thread.Sleep(5s)` or `Task.Delay(5s)` returns immediately and the next read of `DateTime.Now` reflects 5 seconds later. This is the right default: most tests want to skip the wait, not enforce it.

```csharp
MockTimeSystem timeSystem = new(new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc));

await timeSystem.Task.Delay(TimeSpan.FromMinutes(10));

await That(timeSystem.DateTime.UtcNow)
    .IsEqualTo(new DateTime(2026, 1, 1, 0, 10, 0, DateTimeKind.Utc));
```

## Timers and timeouts

A timer moves the clock to its due time as well. The timers that are due on the way fire in the order of their due time, and each callback sees the clock at its own due time, not at the end of the wait. Like a real timer, a callback runs on another thread with the execution context of the code that created the timer, while the thread that moves the clock waits until it completes. When the callback waits for the clock, i.e. for `Task.Delay`, `PeriodicTimer.WaitForNextTickAsync` or `ITimerMock.Wait` of the `MockTimeSystem`, the clock moves on at once, just like the real clock keeps running. When it blocks on anything else, e.g. on another timer through an event or on a lock that the waiting code holds, the clock moves on once it was blocked for one second of real time. A callback that keeps running, e.g. on a busy machine, holds the clock for up to 30 seconds. All timers move the clock on one shared background thread. Another thread that moves the clock at the same time, e.g. a `Task.Delay` or `AdvanceBy` in the test, can move it further while a callback runs.

A timer without a period whose state is a `CancellationTokenSource` is a timeout. This includes the timer of `new CancellationTokenSource(TimeSpan, TimeProvider)` on the [`TimeProvider`](./01-configuring-time.mdx) from `ToTimeProvider()`, a `Timer.New` that cancels the `CancellationTokenSource` it gets as state, and the timer of `Task.WaitAsync(TimeSpan, TimeProvider)`. A timeout never moves the clock on its own: it fires when a wait or `AdvanceBy` moves the clock past its due time, so that an operation with a timeout is not canceled before it starts. A one-shot timer that does other work should therefore not get a `CancellationTokenSource` as state.

```csharp
MockTimeSystem timeSystem = new();
TimeProvider timeProvider = timeSystem.ToTimeProvider();
using CancellationTokenSource cts = new(TimeSpan.FromSeconds(1), timeProvider);

// Throws an OperationCanceledException, with the clock one second later
await Task.Delay(TimeSpan.FromSeconds(5), timeProvider, cts.Token);
```

A wait that its timeout cancels on the way stops the clock at the timeout. This applies to `Task.Delay` and `PeriodicTimer.WaitForNextTickAsync` of the `MockTimeSystem` and to `Task.Delay` on the `TimeProvider`.

:::warning[Waiting only for a timeout]
As a timeout never moves the clock, code that waits for nothing but a timeout, e.g. `Task.Delay(Timeout.InfiniteTimeSpan, timeProvider, cts.Token)`, waits until something else moves the clock. Only `Task.Delay(Timeout.InfiniteTimeSpan)` of the `MockTimeSystem` itself returns immediately with auto-advance.
:::

## Disabling auto-advance

When you need to assert *that* code waited (instead of just letting it through), turn auto-advance off via `MockTimeSystemOptions.DisableAutoAdvance()` and move the clock yourself with `TimeProvider.AdvanceBy(...)` or `TimeProvider.SetTo(...)`:

```csharp
MockTimeSystem timeSystem = new(o => o.DisableAutoAdvance());

Task delay = timeSystem.Task.Delay(TimeSpan.FromMinutes(10));
await That(delay.IsCompleted).IsFalse();

// highlight-next-line
timeSystem.TimeProvider.AdvanceBy(TimeSpan.FromMinutes(10));
await delay; // completes, because the clock has reached the end of the delay
```

With auto-advance off:

| Call                                  | Behavior                                                               |
|---------------------------------------|------------------------------------------------------------------------|
| `Task.Delay`                          | Stays pending until the clock reaches the end of the delay             |
| `PeriodicTimer.WaitForNextTickAsync`  | Stays pending until the clock reaches the next tick                    |
| `Thread.Sleep`                        | Returns immediately without moving the clock                           |
| `Timer`                               | Fires when `AdvanceBy` reaches its due time; `AdvanceBy` waits for it  |

:::warning[Awaiting a delay with auto-advance off]
Awaiting `Task.Delay` before anything advances the clock waits forever. Start the delay, advance the clock (or let another task do it), then await it.
:::

Combine this with the [notifications](./06-notifications.mdx) hooks to assert what your code asked for.

## Waiting until the timers are idle

The timers fire on background threads, so a test that asserts on their effects has to wait for them. Instead of waiting for a margin of real time, wait until the timers are idle with `TimerHandler.WaitUntilIdle()` or `TimerHandler.WaitUntilIdleAsync()`. The timers are idle when no timer is due or moves the clock on its own and no timer callback runs. A callback that waits for the clock does not count, as nothing happens until something else moves the clock. This also holds when only a timeout is left:

```csharp
MockTimeSystem timeSystem = new();
TimeProvider timeProvider = timeSystem.ToTimeProvider();
using CancellationTokenSource cts = new(TimeSpan.FromSeconds(5), timeProvider);
Task delay = Task.Delay(Timeout.InfiniteTimeSpan, timeProvider, cts.Token);

// highlight-next-line
await timeSystem.TimerHandler.WaitUntilIdleAsync();
await That(delay.IsCompleted).IsFalse()
    .Because("only the timeout is left, and a timeout does not move the clock");

timeSystem.TimeProvider.AdvanceBy(TimeSpan.FromSeconds(5));
await That(delay.IsCanceled).IsTrue();
```

With auto-advance off, `AdvanceBy` stops waiting for a callback once it was blocked for one second of real time, or after 30 seconds. Call `WaitUntilIdle()` afterward to also wait for the callbacks that it left running.

Both methods throw a `TimeoutException` that describes the busy timers when they are not idle within the timeout (10 seconds by default). Call them after the code that moves the clock returned, and not from inside a timer callback, which itself keeps the timers busy. A periodic `Timer` with auto-advance never becomes idle, as it keeps moving the clock.

Idle refers to the timers only, including those of the `TimeProvider` from `ToTimeProvider()`. `Task.Delay`, `Thread.Sleep` and `PeriodicTimer` of the `MockTimeSystem` move or wait for the clock on the calling thread and are not tracked. Neither is a callback that continues after it waited for the clock, nor the work that the callbacks start elsewhere, e.g. the continuations of a completed delay on the thread pool.

## Multi-threaded scenarios

All threads share one simulated clock, so two parallel `Sleep(5s)` calls move it by **10 seconds total**, which can be surprising. If your test exercises real parallelism, swap in the [thread-aware provider](./07-thread-aware-provider.mdx) so each async context has its own clock.
