# Auto-advance

By default, `MockTimeSystem` advances its clock every time the code under test waits. A call to `Thread.Sleep(5s)` or `Task.Delay(5s)` returns immediately and the next read of `DateTime.Now` reflects 5 seconds later. This is the right default: most tests want to skip the wait, not enforce it.

```csharp
MockTimeSystem timeSystem = new(new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc));

await timeSystem.Task.Delay(TimeSpan.FromMinutes(10));

await That(timeSystem.DateTime.UtcNow)
    .IsEqualTo(new DateTime(2026, 1, 1, 0, 10, 0, DateTimeKind.Utc));
```

## Timers and timeouts

A timer moves the clock to its due time as well. The timers that are due on the way fire in the order of their due time, on the thread that moves the clock, and each callback sees the clock at its own due time, not at the end of the wait. All timers move the clock on one shared background thread. Another thread that moves the clock at the same time, e.g. a `Task.Delay` or `AdvanceBy` in the test, can move it further while a callback runs, just like the real clock keeps running.

On the [`TimeProvider`](./01-configuring-time.mdx) from `ToTimeProvider()`, a timer without a period whose state is a `CancellationTokenSource`, like the one of `new CancellationTokenSource(TimeSpan, TimeProvider)`, and the timer of `Task.WaitAsync(TimeSpan, TimeProvider)` are timeouts. A timeout never moves the clock on its own: it fires when a wait or `AdvanceBy` moves the clock past its due time, so that an operation with a timeout is not canceled before it starts.

```csharp
MockTimeSystem timeSystem = new();
TimeProvider timeProvider = timeSystem.ToTimeProvider();
using CancellationTokenSource cts = new(TimeSpan.FromSeconds(1), timeProvider);

// Throws an OperationCanceledException, with the clock one second later
await Task.Delay(TimeSpan.FromSeconds(5), timeProvider, cts.Token);
```

A wait that its timeout cancels on the way stops the clock at the timeout. This applies to `Task.Delay` and `PeriodicTimer.WaitForNextTickAsync` of the `MockTimeSystem` and to `Task.Delay` on the `TimeProvider`.

:::warning[Waiting only for a timeout]
As a timeout never moves the clock, code that waits for nothing but a timeout, e.g. `Task.Delay(Timeout.InfiniteTimeSpan, timeProvider, cts.Token)`, waits until something else moves the clock. Only `Task.Delay(Timeout.InfiniteTimeSpan)` of the `MockTimeSystem` itself returns immediately with auto-advance.
:::

## Disabling auto-advance

When you need to assert *that* code waited (instead of just letting it through), turn auto-advance off via `MockTimeSystemOptions.DisableAutoAdvance()` and move the clock yourself with `TimeProvider.AdvanceBy(...)` or `TimeProvider.SetTo(...)`:

```csharp
MockTimeSystem timeSystem = new(o => o.DisableAutoAdvance());

Task delay = timeSystem.Task.Delay(TimeSpan.FromMinutes(10));
await That(delay.IsCompleted).IsFalse();

// highlight-next-line
timeSystem.TimeProvider.AdvanceBy(TimeSpan.FromMinutes(10));
await delay; // completes, because the clock has reached the end of the delay
```

With auto-advance off:

| Call                                  | Behavior                                                               |
|---------------------------------------|------------------------------------------------------------------------|
| `Task.Delay`                          | Stays pending until the clock reaches the end of the delay             |
| `PeriodicTimer.WaitForNextTickAsync`  | Stays pending until the clock reaches the next tick                    |
| `Thread.Sleep`                        | Returns immediately without moving the clock                           |
| `Timer`                               | Fires when `AdvanceBy` reaches its due time, on the advancing thread   |

:::warning[Awaiting a delay with auto-advance off]
Awaiting `Task.Delay` before anything advances the clock waits forever. Start the delay, advance the clock (or let another task do it), then await it.
:::

Combine this with the [notifications](./06-notifications.mdx) hooks to assert what your code asked for.

## Multi-threaded scenarios

All threads share one simulated clock, so two parallel `Sleep(5s)` calls move it by **10 seconds total**, which can be surprising. If your test exercises real parallelism, swap in the [thread-aware provider](./07-thread-aware-provider.mdx) so each async context has its own clock.
